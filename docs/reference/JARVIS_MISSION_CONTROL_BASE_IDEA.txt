JARVIS MISSION CONTROL
Base Idea / Product Concept Sheet
=================================

Document purpose
----------------
This document is the base design reference for a custom web application that acts as the visual control center for the Jarvis LangGraph AI stack.

The goal is to give Jarvis a clean, real-time, "mission control" interface where a user can:

- Talk directly to the Organizer.
- Start and manage jobs.
- Watch the active LangGraph execution in real time.
- See which agent is working, waiting, finished, blocked, or failed.
- See tools being called and what they are doing.
- See readable progress updates instead of raw logs.
- Inspect files changed, commands run, tests executed, and results returned.
- View system health and infrastructure metrics.
- Review completed runs and understand how a job progressed.
- Interrupt, pause, approve, retry, or cancel work when appropriate.

This should become the primary operator interface for Jarvis.

LangSmith Studio can remain available as a developer/debugging interface, but Jarvis Mission Control should be the polished application used day-to-day.


======================================================================
1. PRODUCT VISION
======================================================================

Jarvis should feel like an autonomous computing system rather than a chatbot.

A normal AI interface looks like:

    User -> Chat -> AI response

Jarvis Mission Control should look and behave more like:

    User
      |
      v
    Organizer
      |
      +---- Planner
      |
      +---- Researcher
      |
      +---- Developer
      |       |
      |       +---- Files
      |       +---- Shell
      |       +---- Git
      |       +---- Tests
      |
      +---- Reviewer
      |
      +---- Other specialized agents
              |
              +---- Tools / services / infrastructure

While this happens, the web UI should visually update as work moves through the system.

The user should be able to answer questions such as:

- What is Jarvis doing right now?
- Which agent currently has control?
- What task is that agent working on?
- What did the Organizer delegate?
- Which tools are active?
- What command is currently running?
- Which files have been read or modified?
- What has already completed?
- What failed?
- Why is the job waiting?
- Does Jarvis need my approval?
- How long has this job been running?
- What resources are being used?
- What did the completed job produce?

The interface should communicate all of this without requiring the user to read large raw logs.


======================================================================
2. CORE EXPERIENCE
======================================================================

The main application should have four primary functions:

1. CONVERSATION
   Talk to the Organizer just like a normal AI assistant.

2. LIVE VISUALIZATION
   Watch the agent graph execute in real time.

3. JOB MANAGEMENT
   See current objectives, subtasks, progress, artifacts, failures, and approvals.

4. OBSERVABILITY
   Inspect the underlying events, tool calls, commands, metrics, and history.

4. MAIN UI AREAS
======================================================================

A. ORGANIZER CHAT
-----------------

Purpose:
- Main conversation with Jarvis.
- New jobs can originate here.
- The Organizer can ask clarification questions.
- User can approve or reject actions.
- User can interrupt or add instructions while a job is running.

Possible features:
- Streaming responses.
- Thread history.
- Attach files.
- Drag-and-drop artifacts.
- Job status embedded inside messages.
- Buttons for:
  - Pause
  - Resume
  - Cancel
  - Approve
  - Retry
  - Open run
  - View output
- Switch between conversation threads.
- Start a new objective without losing old run history.

Important design principle:
Chat should not be the only source of truth. It is one interface into the system. The live graph and job state should exist independently from chat.


B. LIVE AGENT GRAPH
-------------------

Purpose:
Show LangGraph execution as a real-time visual graph.

Possible node types:
- Organizer
- Planner
- Researcher
- Developer
- Reviewer
- Security Reviewer
- Deployment Agent
- Browser Agent
- Data Agent
- Shell
- Filesystem
- Git
- Database
- HTTP/API
- Ollama/model server
- Human approval node

Node states:
- IDLE
- QUEUED
- RUNNING
- WAITING
- BLOCKED
- NEEDS APPROVAL
- SUCCEEDED
- FAILED
- CANCELLED
- RETRYING

Suggested visualization:
- Idle: subdued.
- Running: highlighted with animated pulse.
- Completed: check mark.
- Failed: error icon.
- Waiting: clock icon.
- Approval: attention badge.
- Selected node: inspector panel opens.

Edges should also communicate execution:
- Organizer -> Coder activates when work is delegated.
- Coder -> Shell activates when a command runs.
- Shell -> Coder activates when output returns.
- Coder -> Reviewer activates when implementation is submitted for review.

The animation should be driven by actual backend events, not fake timers.

Graph controls:
- Fit graph to screen.
- Zoom.
- Pan.
- Pause visual auto-follow.
- Center on currently active agent.
- Show/hide tools.
- Show/hide completed branches.
- Expand/collapse subgraphs.
- Filter by agent type.
- Filter by event severity.

Clicking a node should show:
- Agent name.
- Current state.
- Current task.
- Started time.
- Elapsed time.
- Current model.
- Current tool.
- Recent events.
- Input summary.
- Output summary.
- Files touched.
- Errors.
- Child tasks.
- Parent task.


C. CURRENT JOB PANEL
--------------------

Purpose:
Give a clean high-level representation of the current objective.

Example:

    Objective
    ---------
    Add user authentication to Jarvis API.

    Progress
    --------
    63%

    Plan
    ----
    [x] Inspect existing API
    [x] Design auth flow
    [x] Add database schema
    [>] Implement endpoints
    [ ] Add tests
    [ ] Run security review
    [ ] Final verification

    Current owner
    -------------
    Developer Agent

    Current action
    --------------
    Implementing token refresh endpoint.

    Blockers
    --------
    None

Progress should preferably be task-based rather than a fake arbitrary percentage.

Possible progress calculation:
- Each planned task has a weight.
- Complete tasks contribute their weight.
- Running tasks can optionally contribute partial progress only when meaningful.
- Unknown/unplanned work can show "indeterminate" rather than inventing a percentage.

Filters:

5. REAL-TIME EVENT MODEL
======================================================================

The application should be event driven.

The frontend should not continuously poll every panel.

Preferred architecture:

    LangGraph / Jarvis backend
             |
             | events
             v
       Event normalization layer
             |
             +---- SSE or WebSocket ----> Browser
             |
             +---- PostgreSQL event store
             |
             +---- Metrics pipeline

The event normalization layer is important.

LangGraph, tools, and infrastructure may produce different event formats. Mission Control should convert them into one common Jarvis event schema.


Example event schema:

{
  "event_id": "evt_123",
  "run_id": "run_456",
  "thread_id": "thread_789",
  "timestamp": "2026-09-07T00:34:10-04:00",

  "category": "tool",
  "type": "file_write",

  "source": {
    "agent": "developer",
    "node": "developer_node"
  },

  "target": "/opt/jarvis/app/main.py",

  "status": "running",

  "message": "Developer is modifying app/main.py",

  "metadata": {
    "tool": "write_file"
  }
}

Possible categories:
- job
- graph
- agent
- task
- tool
- shell
- file
- git
- model
- approval
- system
- artifact
- error

Possible event types:

- Threads

- Subgraphs
- State updates
- Tool calls
- Model streaming
- Checkpoints
- Interrupts

The Jarvis backend should emit events whenever execution changes.

Example conceptual flow:

    User submits objective

        -> Organizer starts

        -> Organizer creates plan

        -> Organizer delegates research

        -> Researcher starts

        -> Search/API tool starts

        -> Tool completes

        -> Researcher completes

        -> Organizer delegates implementation

        -> Developer starts

        -> Developer reads files

        -> Developer edits code

        -> Developer runs tests

        -> Test fails

        -> Developer retries

        -> Test succeeds

        -> Reviewer starts

        -> Reviewer approves

        -> Organizer completes job


Each transition should immediately update the browser.


======================================================================
7. STREAMING TRANSPORT
======================================================================

Two likely options:

OPTION A: SERVER-SENT EVENTS (SSE)
----------------------------------

Best when:
- Server primarily pushes events to browser.
- Browser sends commands using normal HTTP endpoints.
- Simplicity is preferred.

Advantages:
- Simple.
- Built into browsers.
- Easy reconnection.
- Good fit for one-way LangGraph event streaming.

Potential design:

    POST /api/jobs
    GET  /api/jobs/{id}
    GET  /api/jobs/{id}/events     <- SSE
    POST /api/jobs/{id}/pause
    POST /api/jobs/{id}/resume
    POST /api/jobs/{id}/cancel
    POST /api/jobs/{id}/approve


OPTION B: WEBSOCKETS
--------------------

Best when:
- Heavy two-way interaction is needed.
- Lots of interactive runtime commands are expected.
- Multiple realtime dashboards may subscribe.

Advantages:
- Fully bidirectional.
- Good for command/control.

Disadvantages:
- Slightly more complex.

Initial recommendation:
Start with SSE unless Jarvis develops requirements that make WebSockets clearly better.

10. EVENT BUS
======================================================================

Jarvis should eventually have a central internal event bus.

Conceptually:

    LangGraph nodes ----+
                       |
    Tool wrappers ------+
                       |
    Shell executor -----+----> Jarvis Event Bus
                       |
    File manager -------+
                       |
    Infrastructure -----+

The event bus then fans out events to:

    -> Web UI
    -> PostgreSQL
    -> Metrics
    -> Logs
    -> Alerts
    -> Future mobile app
    -> Future voice UI

This prevents the frontend from being tightly coupled to individual agents.


======================================================================
11. TOOL WRAPPERS
======================================================================

Every important Jarvis tool should emit lifecycle events.

Example shell tool:

Before command:

    command_started
    agent: developer
    command: pytest

After command:

    command_completed
    exit_code: 0
    duration_ms: 4210
    summary: 19 tests passed

Example file tool:

Before read:

    file_read
    path: /opt/jarvis/app/main.py

Before write:

    file_write_started

After write:

    file_write_completed
    lines_added: 38
    lines_removed: 7

Example Git tool:

    git_status
    git_diff_created
    git_commit_started
    git_commit_completed

This is how Mission Control knows what is happening.


======================================================================
12. HUMAN-READABLE EVENT SUMMARIES
======================================================================

Raw system events should be retained, but the default activity feed should translate them into readable text.

Raw:

    {
      "type": "tool_start",
      "tool": "shell",
      "args": {
        "command": "pytest"
      }
    }

Displayed:

    Developer -> running test suite

Raw:

    {
      "type": "tool_end",
      "exit_code": 1,
      ...
    }

Displayed:

    Tests finished: 18 passed, 1 failed

The system should never fabricate progress.

If a tool provides no useful progress signal, display:

    Developer -> running integration test suite...

rather than inventing "72%" completion.

======================================================================
25. SECURITY
======================================================================

Mission Control is powerful and should be treated as an administrative interface.

Requirements:
- Authentication.
- HTTPS.
- Secure session cookies or proper token handling.
- CSRF protection where applicable.
- Rate limiting.
- Audit log.
- Role-based permissions if multiple users are ever supported.
- Never expose arbitrary shell execution publicly.
- Avoid sending secrets to the frontend.
- Redact secrets from logs/events.
- Mask API keys.
- Mask passwords.
- Mask private tokens.
- Restrict privileged operations.
- Require approval for destructive actions.

Recommended deployment:
Mission Control should initially be accessible only:
- On local network,
- Via VPN,
- Via an authenticated private tunnel,
or another secure method.

Do not expose an unrestricted Jarvis administrative interface directly to the public internet.

26. SECRET REDACTION
======================================================================

- API keys.
- Bearer tokens.
- Passwords.

31. VISUAL DESIGN DIRECTION
======================================================================

The interface should feel:
- Modern.
- Technical.
- Dense but readable.
- Dark-mode-first.
- High contrast.
- Minimal clutter.
- Serious rather than gimmicky.
- Inspired by mission-control / observability tools.

Avoid:
- Excessive neon.
- Fake sci-fi elements.
- Pointless animations.
- Too many charts.
- Giant glowing buttons.
- Information overload.

Use animation only when it communicates something.

Examples:
- Active graph edge animates.
- Running node gently pulses.
- New event appears.
- Progress transitions.
- Approval card draws attention.

The UI should still be usable for hours at a time.

39. HEARTBEATS / STUCK JOB DETECTION
======================================================================

Mission Control should know whether an apparently running agent is actually alive.

Agents/tools can periodically update:
- Last activity time.
- Current operation.
- Heartbeat.

If there has been no observable activity for a threshold:

    Developer
    POSSIBLY STALLED
    No event for 3m 12s

The system can then:
- Alert the Organizer.
- Retry.
- Ask the user.
- Kill a hung process.

53. DESIGN PRINCIPLES
======================================================================

1. REAL EVENTS ONLY
Never fake activity.

2. HUMAN READABILITY FIRST
Translate low-level events into understandable status.

3. RAW DETAIL AVAILABLE
Allow expansion into technical details.

4. EVENT-DRIVEN ARCHITECTURE
The frontend subscribes to what Jarvis is doing.

5. SEPARATE OBSERVABILITY FROM REASONING
Show actions, state, tools, results, and summaries rather than hidden chain-of-thought.

6. SAFE AUTONOMY
Sensitive actions should be interruptible and approvable.

7. DISTRIBUTED FROM THE START
Even if the first build runs on one machine, event formats should include host/node information.

8. DO NOT OVERBUILD THE MVP
Prove the live experience first.

9. KEEP LANGGRAPH AS THE ORCHESTRATION SOURCE OF TRUTH
Mission Control visualizes and controls it; it should not become a second conflicting workflow engine.

10. KEEP THE EVENT SCHEMA STABLE
Agents and tools can evolve behind a consistent UI contract.

55. DEFINITION OF SUCCESS
======================================================================

Mission Control is successful when the following experience works:

The user opens Jarvis in a browser.

They type:

    "Build a new endpoint that reports the health of every Jarvis service."

Immediately:

- A new job appears.
- Organizer changes to RUNNING.
- Planner becomes active.
- Tasks populate.
- Planner completes.
- Developer activates.
- File reads appear in the activity feed.
- Code changes appear in the file panel.
- Shell activates.
- Test output appears.
- A failed test visibly sends the workflow back to Developer.
- Developer fixes it.
- Tests pass.
- Reviewer activates.
- Reviewer completes.
- Organizer marks the job complete.
- Final files/artifacts are shown.
- The full run remains available in history.

At no point should the user wonder whether the system is frozen or what Jarvis is doing.
